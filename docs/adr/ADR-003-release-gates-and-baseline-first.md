# ADR-003：三条发布硬闸门与基线先行

- 状态：已实施（v2 三轮路线，0.48–0.49 首轮放行）
- 日期：2026-11-26
- 相关：`OpenLeaf-v2-发布门禁总纲.md`、`OpenLeaf-v2.1-阅读类门禁.md`、`OpenLeaf-v2-基线采集报告.md`

## 背景

UI 改造（入口重排、面板开合）的风险与功能开发不同：core 单测全绿、构建 lint 通过，仍可能"按钮找不到、正文跳行、播放被打断"。此前 0.29 P0 开书必崩、0.33 路由漏改、0.46 AMOLED 冷启降级都证明：**自动化门禁测不到 UX 与生命周期顺序**。

同时，一个版本里混合阅读与播放改动会导致"视频未完成阻塞阅读发布"或"阅读通过掩盖视频生命周期问题"。

## 选项

- **A. 沿用旧门禁**：core 全绿 + 冒烟 + 像素回归即可发布——不够，无法证明"动作好找、位置不跳、能力没丢"。
- **B. 三条硬闸门 + 三轮拆分**：①高频动作点按目标；②显隐不导致位置跳动；③既有能力逐项对照无丢失。按阅读类/播放类/视频专轮各自独立门禁、独立放行。
- **C. 只做人工验收**：不可复核、不可签字。

## 决定

选 **B**，并附加两条纪律：
1. **基线先行**：改造前在基线构建上逐项采实机证据；采不到标"阻塞"并说明原因，**不拿源码说明冒充实机基线**。
2. **独立签字**：用户点名项（标注、音频停止、视频音轨、外部字幕）分别签字，不合并成一项；工程前置（构建/lint/core/像素/DB 清单 manifest）不能替代三条体验门禁。

## 后果

- 正面：同一份录屏，工程与 QA 得出同一结论；0.48 真 P1（关键词施加侧丢失）被门禁抓出并在 0.49 修复；0.48 R-B-09"首页上一页未禁用"被证明是 QA 场景误判（书库有 2 本漫画，qa043 是 series 末章、确有上一兄弟章），保留原证据并标注，不误改代码。
- 负面：基线采集成本高（v2 首轮采了 33 个证据、耗时长）；部分环境限制项（MuMu 手势/读屏/内部数值）只能标"环境未实测"，不能签字。
- **逐行判定口径**：点按次数按起始状态分别记录（小说工具展开/隐藏两态各记），迁移前后只比同一起始状态——解决"允许隐藏态 2 次"与"不得增加次数"的冲突。
- **视频专轮必须独立**：涉及 PlayerView 控制层、音轨、外部字幕 SAF、三来源、离页释放、字幕加载时既有的 `setMediaItem` 重绑——生命周期风险与 UI 分组不同，不能当普通按钮重排验收。

## 可迁移要点

1. 任何"迁移类"改造（入口/布局/面板）先采基线，再谈验收。
2. 门禁要写成可勾选的用例表，每条有 ID、基线、实测、证据链接。
3. 阻塞要上报并分类（设备能力/素材/接口/场景误判），不要无限重试，也不要伪造通过。
4. 修复后重跑失败项**和受影响的共用入口**，不只复点原失败按钮。
